# Quake: атрибуция FPU helper через SIGPROF и снимки JIT

## Результат

На двух запусках воспроизведён конкретный путь **выбранный guest-блок 0x112cc → FPU_FLD_32 → mem_readd**. Во время исполнения `mem_readd` этот путь попал в выборку 3 раза при периоде 1100 мкс и 1 раз при 1700 мкс. Это данные для одного JIT call site, не число вызовов и не доля времени функции Quake.

В более широком наборе в `mem_readd` найдено 216 и 117 сэмплов; для 153 и 89 из них верхний адрес возврата совпадает с инструкцией сразу после прямого вызова `mem_readd` из `FPU_FLD_32`. Точные адреса проверены по disassembly этого бинарника. Во всех 153 и 89 наблюдениях следующий адрес возврата находится в JIT-блоке, живом на момент сэмпла; для остальных блоков кроме выбранного 0x112cc соответствующая инструкция вызова по снимку не проверена. Эти данные повышают приоритет H5 (x87/memory helper) для дальнейшего изучения, но не доказывают, что helper избыточен или что его замена ускорит Quake.

## Проверка вызова выбранного блока

Для 0x112cc проверены поколения 5863 и 5865 соответственно, каждый раз по lifecycle trace того же процесса. Снимки этих поколений полны; адрес возврата JIT кадра — смещение 158, сразу после indirect call на смещении 156. Установленная цепочка адресов: sample RIP внутри `mem_readd`, первый return после direct call внутри `FPU_FLD_32`, второй return после вызова внутри актуального поколения блока 0x112cc. Снятые RIP внутри `mem_readd` относятся к участку с установленным frame pointer (до его восстановления). Частота мала, а indirect target не восстанавливался отдельно по регистрам на момент вызова; вывод опирается на наблюдённую цепочку кадров и проверку инструкций.

Часть сэмплов в `mem_readd` приходится на пролог и эпилог, часть на проверку границ страницы и fast path. Это интересная цель для анализа стоимости, но статистическое попадание в instruction address не измеряет точную стоимость инструкции; профилирование и frame pointers изменяют выполнение.

## Эксперимент

Свежая диагностическая сборка форка commit `91774d582069d52f4d3bf04952cb6047dbdc073f`, тот же SDK и два shims предыдущего отчёта; GCC 14, Release `-O3`, `OPT_JIT_BLOCK_TRACE=ON`, `-fno-omit-frame-pointer` для C и C++. SHA-256 бинарника и profiler в `trace-sha256.txt`. Базовая сборка без trace оставлена отдельно. `demo1`, 320×200, SDL dummy, dynamic core, Quake 1.06, EXE/PAK проверены в предыдущем отчёте. Снимались девять EIP из протокола PR #3; каждый запуск отдельным процессом и с собственной lifecycle-трассой.

| Период SIGPROF | Кадры demo | Сэмплы main thread в окне | Все JIT | Из выбранных snapshots | Вне JIT | Совпали с началом линейной инструкции |
|---|---:|---:|---:|---:|---:|---:|
| 1100 мкс | 969 | 3644 | 1876 | 255 | 1768 | 255/255 |
| 1700 мкс | 969 | 2192 | 1332 | 178 | 860 | 178/178 |

Окно demo определено опросом игрового лога, ошибка границы до интервала опроса. В обоих запусках profiler сообщил `lost=0`. Формальная проверка снимков сопоставила SHA/размеры и live generations; линейный disassembly не является полным графом управления. Многопоточные sample records отобраны по main TID. Прочие JIT и non-JIT не объединялись с выбранными блоками. Частоты — не независимые испытания; периоды могут давать систематический aliasing.

## Как собирали стеки

Взята существующая per-thread CPU-time SIGPROF библиотека и добавлен отдельный фиксированный поток из до 8 return addresses; формат исходного RIP-файла не менялся. Чтение кадров из `/proc/self/mem` через `pread`; `process_vm_readv` в этом окружении вернул ENOSYS. Адреса, пределы и возрастание frame pointer проверяются. Тестовая C-программа, собранная с frame pointers без PIE, дала 170/170 записей с адресом возврата непосредственно после вызова spin; lost=0. В Quake часто используется RBP внутри сгенерированного кода, поэтому большая часть кадров не раскрывается: глубина 0 в 2706/3644 и 1696/2192 сэмплов. Цепочки не являются полным unwind, в prologue/epilogue, leaf, tail calls, сторонних библиотеках и JIT могут обрываться или давать ложные связи. Выше отдельно проверен только конкретный путь; прочие `candidate_*` — лишь кандидаты.

Профилированные FPS 71,4 и 112,0 нельзя сравнивать с A/A: включены trace, stack sampling и другая сборка. Общая интенсивность сэмплов не равна счётчику вызовов. `lost=0` не исключает потерю таймерных сигналов, периодический aliasing или ошибки границ окна.

## Следующий различающий эксперимент

Предложение ниже было сформулировано после этой серии; последующие снимки, прототип и тесты описаны в [fpu-read-study](fpu-read-study/README.md).

Повторить targeted capture с EIP 0x10f4a и 0x306bd наряду с 0x112cc и получить реальные live guest bytes и host CFG каждого поколения. В обоих запусках они дали кандидаты JIT → FPU_FLD_32 → mem_readd, но для них в этом эксперименте не было snapshots, поэтому адреса вызовов не верифицированы. Для 0x112cc сопоставить guest-инструкцию x87 с вызовом на offset 156 и проверить, возможно ли сохранить точные semantics при inline read (включая пересечение страниц, guest faults, MMIO, x87 state и динамические изменения страниц). Подготовить минимальный DOS oracle и сравнить с normal core до любой продуктовой модификации. Для оценки скорости нужен отдельный неинструментированный A/B на более стабильном хосте с A/A контролем.

Никакие game assets, raw guest/native snapshots, логи игры, process maps или сырые адреса сэмплов не опубликованы. Исходные снимки существовали только в приватном рабочем окружении и не являются частью этого репозитория. Файлы `fpu-derived.json` содержат EIP и offsets, а `stack-derived.json` — диагностические имена символов и неподтверждённые кандидатные связи. Тесты: 6 тестов native RIP и 9 тестов instruction resolver прошли; оба demo прошли 969 кадров.
