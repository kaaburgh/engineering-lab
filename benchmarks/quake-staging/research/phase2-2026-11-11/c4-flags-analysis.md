# C4: жизненный цикл гостевых флагов в dynamic x86-64 core

Часть 1 (восстановление без `POPFQ`) — kaaburgh/dosbox-staging#14, +11.1%
[+8.8, +13.4]. Здесь — анализ оставшихся сохранений (`PUSHFQ`) и решение,
стоит ли их убирать.

## 1. Состояния и переходы

Шесть арифметических флагов гостя (OF SF ZF AF PF CF) живут в одном из двух
мест:
- **active**: в host RFLAGS (`x64gen.flagsactive = true`), сразу после
  гостевой арифметики, исполненной host-инструкцией;
- **saved**: образ на host-стеке по `[rsp+CALLSTACK]` (8 на SysV, 40 на Win64).

| Переход | Код | Когда |
|---|---|---|
| active → saved | `gen_protectflags`: `PUSHFQ; LEA RSP,[RSP-CALLSTACK]` | перед любым host-кодом, портящим флаги: inline TLB-проверка памяти, вызов helper'а, `add/and` в адресной арифметике |
| saved → active | `gen_needflags`: до C4 `ADD RSP; POPFQ`, после C4 `ADD AL`+`SAHF` (+`LEA RSP`) | гостевая инструкция читает флаги (Jcc, ADC/SBB, SETcc, PUSHF, …) |
| saved → active, образ сохраняется | `gen_needflags_protected` (C4) | условные выходы из блока, LOOPE/LOOPNE, SALC |
| saved → удалён | `gen_discardflags`: `ADD RSP,8+CALLSTACK` | следующая гостевая инструкция перезаписывает все флаги, не читая |
| выход из блока | `dyn_save_critical_regs` → `reg_flags` через образ (маска `FMASK_TEST`) | конец блока, исключение, `BR_Opcode`, переход в диспетчер |

Прерывания доставляются только между блоками, через `reg_flags`. Heavy
debugger проверяет точки останова в диспетчере (`DEBUG_HeavyIsBreakpoint` в
`CPU_Core_Dyn_X86_Run`), то есть тоже на границах блоков, и видит те же
`reg_flags`. Поэтому внутри блока флаги наблюдаемы гостем только тремя
способами: через инструкции, читающие флаги; через выход из блока; через
исключение (EFLAGS в кадре обработчика).

## 2. Сколько и зачем сохраняется (окно demo, C4)

| Событие | Кол-во |
|---|---:|
| `PUSHFQ` (сохранения) | 583.7 M |
| восстановления (все без `POPFQ`): с удалением образа / с сохранением образа | 16.7 M / 20.6 M |
| из них с сохранением RAX рядом с образом | 13.9 M |
| сохранения, образ которых удалён непрочитанным (≈ 583.7 − 37.3) | ≈ 546 M (93.6%) |

Типичная картина в горячем блоке: гостевая арифметика (флаги active) →
доступ к памяти → `PUSHFQ; LEA` перед TLB-проверкой → … → `ADD RSP,0x10`
перед следующей арифметикой. Образ не читается на быстром пути. Он нужен
только если доступ уйдёт в исключение: кадр #PF должен содержать точный
EFLAGS (SDM vol. 3, 6.12), а TLB-проверка (`and/cmp/test`) уже испортила
host-флаги.

## 3. Верхняя граница выигрыша

- In-situ стоимость одного `PUSHFQ; LEA` по инъекции (Phase 1, +4 на место →
  ×1.13): ≈0.26 ns. Все 583.7 M → ≈0.15 s ≈ **4%** CPU-времени окна demo
  комбинированной сборки (C4+C1a+C6+C2). Это граница при удалении *всех*
  сохранений, что невозможно (§4).
- Профиль комбинированной сборки: 10% JIT-сэмплов приходятся на инструкцию
  после `PUSHFQ`. Это завышенная оценка: cpu-clock без PMU, сэмплы
  накапливаются после микрокодовых инструкций (skid).

## 4. Варианты

| Вариант | Корректность | Цена | Вывод |
|---|---|---|---|
| A. Анализ живости внутри блока: не сохранять, если флаги перезаписываются до чтения | **нарушает** точный EFLAGS в кадре #PF/исключения на этом доступе (образ нужен именно там) | средняя: проход по гостевому коду блока до генерации | отклонён без B |
| B. Быстрый путь без порчи флагов (`LEA`, BMI2 `SHRX`, `NOT`, `JRCXZ`) + сохранение флагов только на медленном пути | сохраняет точность (флаги целы до входа в slow path) | высокая: RCX как обязательный scratch (аллокатор), BMI2-детект и fallback, переписать `dyn_read/write_word/byte`, C1a/C1b; `JRCXZ` — 2 uop, быстрый путь длиннее | выигрыш ≤4% минус удлинение быстрого пути; **не реализуется** |
| C. Дешевле само сохранение: `LAHF`+`SETO` в свободный регистр вместо `PUSHFQ` | сохраняет | нужен свободный регистр | микробенчмарк Phase 1: ≈0.6 ns против 0.3–0.8 ns — выигрыша нет |
| D. Не удалять образ (`ADD RSP`) сразу, а переиспользовать слот | сохраняет | мелкая | экономит одну ALU-инструкцию на 546 M; ниже порога измеримости (CV 5–10%) |

## 5. Решение

Большой рефакторинг (B) не оправдан: граница ≈4% на этом хосте, без
доказанного выигрыша. Пересмотреть, если:
- на AMD (или другом CPU) инъекция `apply_flag_injection.py pushf 4` покажет
  стоимость `PUSHFQ` в несколько раз выше 0.26 ns;
- появится общий рефакторинг генерации доступа к памяти (тогда B добавляется
  к нему почти бесплатно).

Проверки, которые понадобятся при любом варианте: `flagrst.asm` (все пути
перезагрузки), `pfprec.asm`/`pfregs.asm` (EFLAGS и регистры в кадре #PF) и
дополнительно тест на EFLAGS в кадре #PF после «мёртвой» арифметики (сейчас
не нужен: поведение не меняется).
