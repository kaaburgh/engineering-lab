## 5. Находки

### 5.1. C6 меняет эмулируемое время: fallback стоит 2 цикла

Только у C6 (и all4) Quake сообщает 326.9 fps вместо 326.7 при тех же 969
кадрах. Причина — учёт циклов на пути `BR_Opcode`:
- `decoder.h`: `++decode.cycles` выполняется до разбора опкода, и
  `dyn_reduce_cycles()` на метке `illegalopcode` списывает и
  нетранслируемую инструкцию;
- `core_dyn_x86.cpp`, `case BR_Opcode`: `CPU_CycleLeft+=CPU_Cycles;
  CPU_Cycles=1;` — бюджет +1;
- `core_normal.cpp`: `while (CPU_Cycles-->0)` после одной инструкции
  оставляет `CPU_Cycles = −1`, то есть списывает ещё 2.

Итого: каждая инструкция через fallback стоит 2 эмулируемых цикла,
транслированная — 1. C6 убирает ≈1.89 M fallback'ов, это ≈1.89 M циклов
(≈1.9 ms при 1 M циклов/ms), что совпадает с 2.9660 s → 2.9642 s.

Проверка: диагностическая сборка C6, где к каждой новой транслированной
инструкции добавлен `++decode.cycles`, даёт снова ровно 326.7 fps (2 из 2
прогонов; `data/bench-c6cyc-*`). Поведение инструкций не меняется. PR
оставляет 1 цикл (как у всех транслированных инструкций) и описывает
альтернативу.

### 5.2. Ошибка normal core: неверный EIP при #PF в CALL

STACKOPS на normal core (и в `main`, и во всех вариантах) даёт
`pf call eip got=E8C exp=E87`: при #PF на записи адреса возврата CALL
гостевой обработчик видит EIP следующей инструкции, а не самого CALL.
Dynamic core выдаёт правильный EIP. Это отдельный дефект корректности;
здесь он не исправлялся (правило: не смешивать с изменениями
производительности).

Причина по исходнику (`main` 27b1b7c):
- `src/cpu/core_normal/prefix_66.h`, `CALL Jd` (0xE8): `SAVEIP;
  Push_32(reg_eip); reg_eip+=addip;`. `SAVEIP` переводит `reg_eip` на
  следующую инструкцию до записи в стек, а legacy-путь `PAGING_PageFault`
  берёт текущий `reg_eip` как EIP сбоя;
- `src/cpu/core_normal/prefix_none.h`, `CALL Jw`: то же с `Push_16`;
- `CALL Ev` (группа 5, /2): `reg_eip` присваивается адрес цели ещё до
  `Push_16(GETIP)`, поэтому при сбое кадр получит EIP цели (тестом пока не
  покрыто).

Исправление — записывать адрес возврата (`GETIP`) до изменения `reg_eip`.
Проверка: STACKOPS `--core normal` → `fails=00000000`, остальные гейты без
изменений.

### 5.3. Неточный #PF для x87 memory-форм (из Phase 1) остаётся

C1a намеренно сохраняет поведение `main`: EIP начала блока и устаревшие
регистры при #PF на x87 m32/m64. Исправление — отдельное
correctness-изменение для всех x87 memory-форм, с гейтом `pfprec`
(везде `E=I R=ok`).

### 5.4. C3: снижение числа входов в диспетчер не даёт времени

9.7 M избежанных проходов через диспетчер (медиана baseline 4.83 s CPU на
окно demo) дают +2.0% [−0.1, +4.2], то есть ≈10 ns на проход (≤20 ns по
верхней границе CI).
Диспетчер на этом хосте не узкое место. Результат сохранён как
отрицательный (kaaburgh/dosbox-staging#18 помечен «не для merge»).

### 5.5. C2: эффект малый

Inline PUSH/POP устраняют 105 M вызовов helper'а, но дают только
+3.4% [+1.2, +5.8]: ≈1.5 ns на операцию. Вызов checked-helper'а с
прямым TLB-попаданием, видимо, дёшев; в p2-a и p2-c CI по отдельности
включают 0.

### 5.6. C4, часть 2: оставшиеся `PUSHFQ` — граница ≤4%, рефакторинг не оправдан

Подробно — [c4-flags-analysis.md](c4-flags-analysis.md). 93.6% из 583.7 M
сохранений удаляются непрочитанными, но образ нужен для точного EFLAGS в
кадре исключения на следующем доступе к памяти. Убрать сохранение корректно
можно только с быстрым путём TLB-проверки, не портящим флаги (BMI2 + `JRCXZ`,
переписать все генераторы доступа к памяти). In-situ цена `PUSHFQ` ≈0.26 ns
(инъекция) → граница ≈4% при удалении *всех* сохранений. Не реализуется.

### 5.7. Профиль комбинированной сборки (C4+C1a+C6+C2)

`data/perf-demo-window-all4.json` (2807 сэмплов главного потока, cpu-clock):
JIT-код 74.7%, C++ DOSBox 15.9%, SDL 7.0%. Профиль плоский: 30 самых горячих
блоков дают 26%. В JIT-коде 51% сэмплов на инструкциях доступа к памяти
(inline TLB-проверка), ≈10% сразу после `PUSHFQ` (skid). Остатки в C++:

| Путь | Доля | Оценка выигрыша | Решение |
|---|---|---|---|
| VGA chained-запись кадра (C5): `mem_writed_checked_dcx64` → `PageHandler::writed_checked` → `VGA_ChainedVGA_Handler::writed` | ≈4.8% | работа handler'а (две записи + change tracking) неустранима; девиртуализация ≈1 косвенный вызов на dword → ≤1%; блочный REP MOVSD → ≤1.6% при сложной семантике (рестарт, прерывания, DF) | не реализуется |
| диспетчер: `MakeCodePage` + `CPU_Core_Dyn_X86_Run` | ≈5% | C3 убирает половину входов, но поверх комбинации эффекта нет (all6 vs all5 −0.5%); пропуск `MakeCodePage` для той же страницы ≤1% | не реализуется |
| `FPU_FST_32` + `mem_writed` | ≈2.6% | C1b | kaaburgh/dosbox-staging#19 |
| `FPU_FLDCW_DH` + `mem_readw` | ≈0.9% | ≤0.5% | не реализуется |

### 5.8. Единичный недетерминированный прогон

В серии p2-d один прогон `all4` (run 67) дал 969 кадров за 3.4 s гостевого
времени (283.4 fps) вместо 2.96 s и 5.28 s CPU вместо ≈3.5 s. Ни до, ни после
это не повторилось: всего у `all4` 1 из 92 прогонов, у baseline 0 из ≈180;
стресс-тест с тремя параллельными сериями (60 + 60 прогонов base/all4,
`data/det-parallel-*`) — все 120 детерминированы. Причина не установлена:
логи прогона не сохраняются; в fixed-режиме основной цикл детерминирован
(`increase_ticks` меняет только число тиков за итерацию); аудит вызовов
`gen_needflags` (C4 портит AL/AH, сохраняя RAX только если в нём гостевой
регистр) не нашёл места, где RAX — неотслеживаемый временный регистр.
Меры: `pooled_compare.py` теперь отбрасывает блоки с отличающимся гостевым
результатом и сообщает о них; блок с run 67 исключён из анализа p2-d.
Наблюдение остаётся открытым: при повторении нужно сохранять конфиг/лог и
сравнить с отдельными вариантами (C1a, C2, C4, C6).

## 6. Ограничения

- Один хост: Intel VM без PMU. AMD (где стоимость `POPFQ` может отличаться),
  Windows (Win64 `CALLSTACK`=40 проверен только рассуждением), macOS и MSVC
  не проверялись.
- Одна нагрузка (Quake 1.06 demo1). Другие игры могут иметь другое
  распределение (больше BT memory-форм, меньше x87).
- В CPU-время главного потока входит SDL-презентация (≈14% в харнессе), поэтому
  ускорение собственно эмуляции CPU больше указанного.
- Valgrind/callgrind непригоден (Phase 1 HANDOFF §4); стоимость оценивалась
  счётчиками, инъекцией и A/B.
- Счётчики сняты на отдельных инструментированных сборках (код больше, для
  времени не используются).

   #PF в CALL на normal core (§5.2), двойной учёт циклов в fallback (§5.1) —
   по решению мейнтейнеров, т. к. меняют эмулируемое поведение/время.
3. Повторить тайминги на выделенном хосте с A/A, на AMD (цена `POPFQ`/
   `PUSHFQ`: `apply_flag_injection.py`) и на Windows (Win64 `CALLSTACK`).
4. Структурные изменения генератора (доступ к памяти без порчи флагов,
   распределение регистров между блоками) — только как отдельный проект с
   предварительной оценкой выигрыша.
5. Наблюдение §5.8: при повторении — сохранить конфиг и лог прогона.

## 8. Воспроизведение

```bash
# гейты (на каждый бинарник, оба ядра; FLAGOPS с --cycles max)
nasm -f bin -o FLAGRST.COM extras/jit-audit/tests/flagrst.asm
python3 extras/jit-audit/tools/run_dos_test.py --dosbox <dosbox> --com FLAGRST.COM --core dynamic --runtime-cwd <checkout> > out.txt
python3 extras/jit-audit/tests/check_flagrst.py out.txt
gcc -O2 -o flag_restore_check extras/jit-audit/microbench/flag_restore_check.c && ./flag_restore_check

# счётчики
python3 extras/jit-audit/instrumentation/apply_jit_counters.py <checkout-copy>
python3 extras/jit-audit/tools/count_quake.py --dosbox <counters-build> --game game --runtime-cwd <checkout>

# время (пример серии p2-c)
python3 extras/jit-audit/tools/bench_quake.py --variant base=<base> --variant base2=<base> \
  --variant c1a=<c1a> --variant pr9=<pr9> --variant pr10=<pr10> --variant c2=<c2> \
  --variant c3=<c3> --variant c4=<c4> --variant c6=<c6> --variant all4=<all4> \
  --game game --runtime-cwd <checkout> --cycles 1000000 --blocks 12 --warmups 2 \
  --seed 111003 --out p2-c.csv
python3 extras/jit-audit/tools/pooled_compare.py p2-a.csv p2-b.csv p2-c.csv --ref base base2
```
