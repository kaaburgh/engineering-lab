# Проверка kaaburgh/dosbox-staging#11 и kaaburgh/engineering-lab#2

2026-11-09. Обе PR — работа другого агента в другом окружении (Xeon Platinum
2.5 GHz, trace-сборка fork `91774d5`, SIGPROF + 8 слов стека). Проверка
выполнена на данных этой Phase 1 (perf DWARF, полный дамп поколений JIT,
точные счётчики `JitCounters`, приватные guest-байты Quake 1.06 с теми же
хешами) и новыми прогонами. Сырые байты/адреса не публикуются.

## Что это меняет в Phase 2

1. **C6 расширяется и поднимается.** Пробел — не только bit-test, а
   `BT/BTS/BTR/BTC` + `SETcc` + `SAHF/LAHF`, и каждый fallback стоит полной
   передачи x87-состояния, потому что эти инструкции стоят внутри
   x87-тяжёлых функций (`R_RecursiveWorldNode`, `R_ClipEdge`). Минимальная
   реализация для Quake: регистровые формы `BT/BTR/BTS/BTC` (горячие
   `bt edi,ebx` / `btr edi,ebx`), `SETcc r/m8`, `SAHF`/`LAHF` (готовый образец
   — `dyn_sahf` в `core_dynrec/decoder.h`). Это ≈1.95 M fallback за окно
   (≈1.3–1.7%), низкий риск, точная проверка счётчиком `fallback_opcode`.
   Лучший кандидат для **первого** PR Phase 2 по соотношению риск/усилие;
   по потенциалу C1a остаётся первым.
2. **Гейт для C6** — новый `tests/bitops.asm` (kaaburgh/dosbox-staging#12):
   34 случая, CF снимается через `SBB` (не `SETcc`), memory bit string с
   индексами 37/40/−1/−32, 16-битные формы, `SETcc`, `SAHF/LAHF` и оба
   x87-идиома сравнения; ожидаемые значения по SDM; 0 отклонений на normal
   и dynamic base; негативный контроль ловит подмену двух ожиданий. Тест
   PR #11 стоит сохранить как дополнительный.
3. **H2/H3 не снимать.** Их стоимость — в inline-коде JIT (self 2.1% и
   5.1%), что относится к C4 (флаги) и к качеству inline TLB-доступа, а не к
   helpers. Вердикты engineering-lab#2 по H2/H3 основаны на неверной единице
   измерения (только helper-трафик).
4. **Ранжирование x87 не меняется:** x87-загрузки (C1a) остаются крупнейшей
   низкорисковой целью; `SAHF`/`SETcc` из C6 — вторая, меньшая часть
   x87-стоимости (сравнения), которую можно убрать независимо.
5. **Измерения:** если пол engineering-lab#2 подтвердится данными, M0.3
   (время) нужно выполнять в том окружении; первая проверка — PR #10 против
   base с двумя плацебо-метками: ожидается ≈+9% при интервале ±1–2%.
6. **Атрибуция:** две независимые методики (8 слов стека + эвристика
   «ближайший блок» vs DWARF unwind + сопоставление по времени поколения)
   дают одинаковые helper-доли — атрибуция helper→блок считается надёжной.
   Эвристика «ближайший блок по native-адресу» требует проверки в каждом
   случае (сами авторы исправили ошибку с `0x2F5C9`).
