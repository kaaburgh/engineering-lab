# Phase 1 — кандидаты оптимизации (ранжированные гипотезы)

Данные: perf-профиль окна demo (`data/perf-demo-window-base.json`),
**точные частоты событий** окна demo (`data/counts-demo-window-base.json`,
evidence §4), инъекция стоимости флагов (`data/bench-flag-injection-*`),
микробенчмарк, исходники `src/cpu/core_dyn_x86/`. Окно demo ≈ 5.9–6.0 s CPU
main thread (fixed cycles 1 000 000). Проценты — доля этого окна на Intel
Emerald Rapids с SDL dummy/software презентацией (≈14% окна уходит на
презентацию; на хосте с GPU-выводом доли JIT-путей выше). Ожидаемое
ускорение **не назначается**; «граница» — сколько стоит устраняемая работа
сейчас (частота × стоимость события).

## C1. x87 m32 загрузки: `FPU_FLD_32 → mem_readd`

1. **Hot path:** `FLD/FADD/FMUL/FSUB/FCOM… m32` (`D8 /r`, `D9 /0`, `DA /r`,
   `DB /0`) в блоках `0x306bd`, `0x10f4a`, `0x10ca0`, `0x30b20`, `0x112cc`,
   `0x2f5cf`.
2. **Почему дорого:** на каждую загрузку — вызов из JIT (сброс volatile
   host-регистров с guest-значениями, `PUSHFQ`), затем `FPU_FLD_32` →
   `mem_readd` (второй call, 4 push/pop пролога).
3. **Частота и стоимость:** 152.4 M вызовов за окно (157 k/кадр); 7.3% окна
   включительно → ≈2.8 нс helper-части на вызов + JIT-сторона.
   PR #10 доказал, что inline TLB fast path покрывает 99.98% этих загрузок
   (вызовы `FPU_FLD_32` → 0, TLB-промахов +30.8 k), и на этом хосте дал
   объединённо **+8.7% [+5.0, +12.6]** (evidence P3) — это оценка того, что
   может дать C1a, поскольку скорость определяется быстрым путём.
4. **Изменение C1a (рекомендуется):** тот же inline fast path, что в PR #10,
   но **промах → legacy-путь** (`mem_readd` через helper, без `_checked` и без
   deferred exception stub). Минимальная форма: `dyn_read_word` с
   параметризованными slow-path функциями (`*dst = mem_readd(addr); return
   false;`). Семантика baseline сохраняется полностью, включая legacy #PF.
   C1b — PR #10 как есть (точные #PF), C1c — PR #9 (только C++).
5. **Механизм:** убрать call/ret, пролог `mem_readd`, сброс/перезагрузку
   регистров вокруг вызова для 99.98% загрузок.
6. **Риски:** C1a — семантика неизменна (кроме heavy-debugger BPMR на
   TLB-попадании — как у integer-загрузок); рост кода ~2.5× для x87-блоков
   (меньше, чем у PR #10, без exception stubs). C1b — behaviour change (S5).
7. **Опровергающий эксперимент:** (а) `pfprec` на C1a должен дать
   **побайтно тот же вывод, что base** — иначе семантика изменилась;
   (б) счётчик `FPU_FLD_32` (через legacy-обёртку) должен упасть > 99%;
   (в) на стабильном хосте: если ускорение < половины оценки helper-части
   (≈3.5%) при неизменной гостевой работе — модель стоимости неверна.
8. **Измерение:** счётчики (детерминированно), затем время на выделенном
   хосте с A/A.

## C2. Inline fast path для стековых PUSH/POP

1. **Hot path:** `PUSH r32`, `POP r32`, `CALL rel32` (push адреса возврата),
   `RET` (pop).
2. **Почему дорого:** `dyn_push`/`dyn_pop` **всегда** вызывают out-of-line
   `mem_writed_checked`/`mem_readd_checked` (`decoder.h` ~716–760), хотя
   для обычных загрузок/записей есть inline TLB путь.
3. **Частота и стоимость:** 65.4 M push + 39.5 M pop = 104.9 M вызовов за
   окно; self 2.6% + 2.0% → ≈2.6 нс на вызов + JIT-сторона.
4. **Изменение:** `dyn_write_word`/`dyn_read_word` (inline TLB, промах → те
   же `_checked` helpers) с сохранением порядка «ESP меняется только после
   успешной записи» (`NEWESP`).
5. **Механизм:** быстрый путь без call/ret и сброса регистров.
6. **Риски:** низкие — семантика исключений та же (checked → checked);
   проверить `cpu.stack.mask` (16-битный стек), `PUSH ESP`, cross-page push.
7. **Опровержение:** счётчики `push_helper_calls`/`pop_helper_calls` должны
   упасть > 90% — зонд уже показал, что 99.97% PUSH и 99.99% POP попадают в
   прямой TLB в пределах страницы; guest-тесты стека (experiment-plan E2) —
   ожидаемые архитектурные значения.
8. **Измерение:** счётчики, затем время.

## C3. Dispatcher на RET/косвенных переходах (H4, уточнён)

1. **Hot path:** `RET`, `JMP/CALL r/m`, `IRET` → `BR_Normal` →
   `CPU_Core_Dyn_X86_Run`.
2. **Почему дорого:** на каждом входе `MakeCodePage` (+`mem_readb_checked`),
   `FindCacheBlock`, проверка FPU-синхронизации, вход в `gen_runcode`.
   В исходнике: «Maybe check if we staying in the same page?».
3. **Частота и стоимость:** 18.0 M входов за окно (18.6 k/кадр); 3.6% self →
   ≈11 нс на вход.
4. **Изменение:** минимально — пропуск `MakeCodePage`, если цель в той же
   валидной code page; шире — inline-кэш цели RET в JIT.
5. **Механизм:** меньше работы на вход.
6. **Риски:** средние — инвалидация страниц, смена CS/режима/CR3, SMC,
   heavy-debugger проверки в `restart_core`.
7. **Опровержение:** доля входов, где цель в той же code page, < 50% →
   минимальный вариант снимается. Зонд: **67.5%** — критерий пройден;
   осталось показать, что пропуск `MakeCodePage` безопасен при SMC/CR3/CS.
8. **Измерение:** счётчики + время.

## C4. Сохранение/восстановление guest-флагов (`PUSHFQ`/`POPFQ`)

1. **Hot path:** `gen_protectflags()` перед каждой inline TLB-проверкой и
   вызовом helper (`PUSHFQ; LEA RSP,-8`), `gen_needflags()` (`ADD RSP,8;
   POPFQ`) перед следующим потребителем флагов. Флаги сохраняются без
   анализа живости.
2. **Почему дорого:** `POPFQ` — микрокодовая инструкция.
3. **Частота и стоимость (CONFIRMED):** 604 M `PUSHFQ` и 37.3 M `POPFQ` за
   окно. Инъекция in situ: ≈10–12 нс на `POPFQ`, ≈0.3 нс на `PUSHFQ` →
   **≈6% + ≈3% ≈ 9% окна** на этом Intel-хосте.
4. **Изменение:** (a) точное дешёвое восстановление арифметических флагов
   (`FMASK_TEST` = CF/PF/AF/ZF/SF/OF) без `POPFQ` — например, `SAHF` для
   CF/PF/AF/ZF/SF и `ADD AL,0x7F` для OF из сохранённого образа, с временным
   регистром; (b) анализ живости флагов в блоке, чтобы не сохранять мёртвые
   флаги (уменьшает и `PUSHFQ`); (c) долгосрочно — TLB-проверка без изменения
   флагов (BMI2 `SHRX`, `LEA`, `NOT`, `JRCXZ`), тогда сохранение не нужно.
5. **Механизм:** убрать `POPFQ` (a) / `PUSHFQ`+`POPFQ` (b, c).
6. **Риски:** средние для (a) (точность OF/AF, DF/TF/AC не должны меняться,
   регистр-давление), высокие для (b)/(c) (живость через выходы блока,
   исключения, helpers).
7. **Опровержение:** повторить инъекцию на целевых AMD-хостах; если
   стоимость `POPFQ` там < 2 нс, вклад < 1.5% → снизить приоритет.
   Корректность: дифференциальный тест флагов (все ALU-операции × входные
   флаги × memory-операнд между производителем и потребителем) против
   normal core.
8. **Измерение:** счётчик `POPFQ` → ~0 при (a); затем время.

## C5. Запись кадра в VGA (`0x10572`)

1. **Hot path:** копирование кадра в chained VGA-память.
2. **Почему дорого:** каждый dword — TLB-промах inline-записи →
   `mem_writed_checked_dcx64` → виртуальный `VGA_ChainedVGA_Handler::writed`.
3. **Частота и стоимость:** 15.75 M записей = 16 000 dword/кадр (ровно кадр
   320×200), ≈2.2% → ≈8 нс на dword.
4. **Изменение:** блочная запись для строковых операций в handler-страницы
   или более дешёвый путь chained-записи.
5–6. Меньше виртуальных вызовов; риски средние (VGA change tracking, банки).
7. **Механизм подтверждён по исходнику:** `dyn_string` (`core_dyn_x86/string.h`)
   опускает `REP MOVSD` в JIT-цикл `dyn_read_word` + `dyn_write_word` на
   каждый элемент; для VGA (нет прямого TLB-указателя на запись) каждый dword
   уходит в slow path → `mem_writed_checked_dcx64` → виртуальный
   `VGA_ChainedVGA_Handler::writed`. Опровержение: блочный путь не уменьшает
   `write_word_slow_path` (16 000/кадр) или меняет хеши кадров.
8. Счётчики + скриншот-хеши кадров.

## C6. Fallback в normal core: `BT`/`SETcc`/`SAHF` не транслируются

1. **Hot path / guest:** `bt edi,ebx` и `btr edi,ebx` в цикле отсечения по
   плоскостям `R_RecursiveWorldNode` (`0x2F5C6`, `0x2F6A6`; функция
   идентифицирована в kaaburgh/dosbox-staging#11, маркеры подтверждены
   здесь); x87-сравнения GCC `fnstsw ax; sahf` (в т.ч. `R_ClipEdge`,
   `0x3071E`) и `fnstsw ax; and ah,45h; …; sete al`.
2. **Почему дорого:** `BR_Opcode` → выход из JIT → `sync_dh_fpu_and_run_normal_core()`
   (полная передача x87-состояния туда и обратно, т.к. функции x87-тяжёлые)
   → одна инструкция в normal core → вход через dispatcher.
3. **Частота и стоимость:** 1.95 M за окно (2 008/кадр), все `BR_Opcode`:
   `BT` 1.37 M (70%), `SETE` 0.30 M, `SAHF` 0.18 M, `BTR` 33 k, `BTS` 4 k,
   `SETLE` 3 k; остальное — системные инструкции CWSDPMI. ≈1.3% (perf) +
   ≈0.4% лишних входов в dispatcher.
4. **Изменение:** транслировать регистровые формы `BT/BTS/BTR/BTC`
   (`0F A3/AB/B3/BB/BA`, mod=3), `SETcc r/m8` (`0F 90–9F`), `SAHF`/`LAHF`
   (образец — `dyn_sahf` в `core_dynrec/decoder.h`). Memory-формы `BTx`
   (bit string) могут остаться на fallback.
5. **Механизм:** убрать выход из JIT и синхронизацию x87 на каждую из
   ~1.9 M инструкций.
6. **Риски:** низкие; аккуратно — CF и undefined-флаги `BT` (как в normal
   core), маскирование индекса (mod 16/32), `SAHF` не трогает OF.
7. **Опровержение:** `fallback_opcode` должен упасть на ≈1.88 M (до
   ≈60 k системных); `tests/bitops.asm` — 0 отклонений на dynamic и
   совпадение с normal core; если время не меняется при падении счётчика —
   стоимость fallback переоценена.
8. **Измерение:** счётчики, затем время (ожидаемо мало, ~1–2%: нужен тихий
   хост). Подробности и проверка чужих выводов — [peer-review-dosbox11-lab2.md](peer-review-dosbox11-lab2.md).

## Решение: x87 или другой hotspot?

- **x87 стоит продолжить, но не в форме PR #9 и не PR #10 «как есть».**
  PR #9 исчерпан (малый потенциал). PR #10 доказал механизм, но смешал
  оптимизацию с изменением семантики. C1a берёт выигрыш PR #10, оставляя
  семантику baseline, и проверяется побайтным совпадением `pfprec` с base.
- **Самая крупная найденная статья — не x87, а флаги (C4, ≈9%).** Это
  отдельная исследовательская линия с более высоким риском; её стоит
  начинать с измерения стоимости `POPFQ` на AMD и с дифференциального теста
  флагов, а не с реализации.
- **Лучшее соотношение «ускорение / риск / доказуемость» — C1a**, сразу за
  ним C2 (тот же механизм, ещё меньше кода, меньше граница).
- **C6 — самый дешёвый и безопасный шаг** (меньший потенциал, ≈1.5%); его
  можно делать первым или параллельно как отдельный PR: гейт уже готов
  (`tests/bitops.asm`), эффект проверяется счётчиком.
