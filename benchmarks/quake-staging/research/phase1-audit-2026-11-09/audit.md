# Phase 1 — независимый аудит исследований и оптимизаций JIT (Quake 1.06)

Дата: 2026-11-09. Объект: `kaaburgh/dosbox-staging` PR #1–#10 и отчёты в
`benchmarks/quake-staging/`. Предыдущие отчёты рассматривались как источники
гипотез; каждое существенное утверждение перепроверено независимо (другой
хост и CPU, собственные сборки, собственный профайлер и тесты). Подробная
таблица доказательств — [evidence.md](evidence.md), ранжирование —
[candidates.md](candidates.md), план — [experiment-plan.md](experiment-plan.md),
воспроизведение — [HANDOFF.md](HANDOFF.md).

## 1. Краткие выводы

1. **Профиль Quake воспроизводится.** Тот же набор горячих guest-блоков и
   helper-цепочек получен на Intel Emerald Rapids с Linux `perf` (DWARF unwind)
   вместо SIGPROF-preload. Атрибуция RIP → поколение блока надёжна на уровне
   блоков (95.9% JIT-сэмплов сопоставлены живому поколению по времени и адресу).
2. **x87-путь `FPU_FLD_32 → mem_readd` реален, но ограничен:** 7.3% времени
   окна demo включительно (152 M вызовов за окно). Объединённая оценка
   ускорения PR #10 на этом хосте — **+8.7% [+5.0, +12.6]** (28 блоков,
   плацебо ±0.3%), т.е. заявка PR #10 (+9.59%) правдоподобна; превышение над
   helper-долей указывает на экономию и на JIT-стороне вызова.
3. **PR #9 семантически нейтрален** (по построению и по тесту), даёт
   небольшой выигрыш в машинном коде helper; ускорение (+1.9% [−1.9, +5.7])
   не отличимо от шума.
4. **PR #10 — не нейтральная оптимизация.** Он переводит x87 m32-загрузки с
   legacy-механизма вложенного page fault на точные исключения dynamic core.
   Это **исправляет** ранее не задокументированное отклонение baseline
   (guest #PF handler видит EIP начала JIT-блока и устаревшие регистры), но
   только для части x87-форм. Все 36 оракулов PR #10 и fault-тесты PR #9
   к этому отклонению нечувствительны.
5. **Шум измерений — главный блокер, и он не в гостевой работе.** Даже при
   детерминированной гостевой нагрузке (fixed cycles, одинаковые 3.0 guest-s
   во всех 114 прогонах) CPU-время хоста гуляет с CV 6–10%, а оценки разных
   серий для одной пары расходятся (PR #10: +4.2% в 8 блоках, +10.5% в 20).
   Эффект PR #10 (≈9%) различим только при ≥ 20 блоках с двумя плацебо-
   метками; эффект PR #9 (≈2%) — неразличим. Для малых эффектов нужны точные
   счётчики событий, инъекция стоимости и выделенный хост.
6. **Частоты теперь точные.** Счётчики в отдельной сборке (guest-результаты
   идентичны base) дают за окно demo: 152.4 M вызовов `FPU_FLD_32`,
   104.9 M stack-helper вызовов, 18.0 M входов в dispatcher, 37.3 M `POPFQ`
   и 604 M `PUSHFQ` в сгенерированном коде. PR #10 по счётчикам убирает
   100% вызовов `FPU_FLD_32` (fast path покрывает 99.98% загрузок).
7. **Самая крупная найденная статья — не x87, а сохранение/восстановление
   guest-флагов** вокруг inline-доступа к памяти: инъекция in situ даёт
   ≈10–12 нс на `POPFQ` и ≈0.3 нс на `PUSHFQ`, итого **≈9% окна demo** на
   этом Intel-хосте. Далее: x87 m32 (≈7.3%), stack PUSH/POP (≈4.6%),
   dispatcher (≈3.6%), запись кадра в VGA (≈2.2%), fallback в normal core
   (≈1.3%; все — неподдержанные dynamic core `BT`/`SETcc`/`SAHF` и системные
   инструкции CWSDPMI, ни одного из-за SMC). Зонды подтверждают применимость
   C2 (99.97–99.99% stack-доступов попали бы в inline fast path) и C3 (67.5%
   входов в dispatcher — в ту же code page).

## 2. Реконструкция цепочки доказательств

`Quake guest instructions → JIT translation → native code → helper calls → CPU cost`

| Звено | Что было у предыдущих исследований | Что подтверждено здесь | Остаточные ограничения |
|---|---|---|---|
| Guest-инструкции горячих блоков | Снимки живых guest байтов (PR #2), COFF-сопоставление | Те же EIP горячие; живые подменённые константы `surf8` видны в native коде | Disassembly guest-блоков приватно; соответствие исходникам id — на уровне семейств функций |
| JIT-трансляция | Lifecycle trace + снимки выбранных блоков (PR #1–#4) | Полный дамп всех поколений (7 733) с временем создания/очистки; размеры и число call sites совпадают с PR #2/#4 | Дамп guest-байтов читает только через существующий TLB (без handler) |
| Native → guest | SIGPROF RIP + lifecycle join (PR #3/#4) | perf `--clockid monotonic` + собственный join по (время, адрес) | Инструкционный уровень искажён skid’ом таймерного сэмплинга (E9) |
| Helper ← JIT call site | Frame-pointer стеки (trace build `-fno-omit-frame-pointer`), часть стеков глубины 0 | DWARF unwind в **release**-коде: 91% `mem_readd` ← `FPU_FLD_32`; 2 605 helper-сэмплов привязаны к вызывающему блоку | Атрибуция только первого JIT-кадра; глубже JIT-кадров unwind невозможен (RBP = `&cpu_regs`) |
| Стоимость | Доли сэмплов, без частот | Доли сэмплов (perf) + **точные частоты событий** (сборка JitCounters, evidence §4) + стоимость на событие (микробенчмарк и инъекция in situ) | Нет hardware PMU: нет cycles/IPC/cache-miss; callgrind на JIT DOSBox в этом окружении непригоден (evidence P5) |

**Частота, стоимость, доля.** Прежние отчёты корректно оговаривали, что
сэмплы ≠ число вызовов, но ранжировали кандидатов по сэмплам. Здесь три
величины разделены: доля времени — perf; частота — точные счётчики (число вызовов
helper/dispatcher и исполнений инструкций в JIT-коде); стоимость одной операции —
микробенчмарк и инъекция дополнительных экземпляров операции в реальный
код (in situ). Это меняет картину для флагов: `PUSHFQ` дёшев на одно
исполнение (≈0.3 нс), но исполняется 604 M раз за окно; `POPFQ` в 30–40
раз дороже на исполнение и при 37 M исполнений даёт ≈6% окна, хотя
сэмплов после него меньше.

**Соответствие профилей поколениям JIT.** В этой работе каждый сэмпл
сопоставляется поколению по времени, а не только по адресу. Прежние
перекрёстные ссылки «профиль одного прогона ↔ снимок другого прогона»
(например, отчёт PR #5, разные периоды SIGPROF) остаются валидными только
для блоков, чьи поколения стабильны в demo — здесь это подтверждено
(183 очистки на 7 733 поколения за весь прогон).

**Влияние инструментирования.** Прежние helper-атрибуции сделаны на trace
сборках с `-fno-omit-frame-pointer`, то есть на другом машинном коде helper.
Здесь профилируется код, идентичный release (исследовательский perf-map
трогает только создание/очистку блоков). Качественный вывод про пролог
`mem_readd` сохраняется: в release-коде быстрый путь `mem_readd` тоже
сохраняет 4 callee-saved регистра (из-за встроенного медленного unaligned пути).

**Неподтверждённое.** В PR #7 ~14% сэмплов приходились на `ld-linux` — здесь
0 сэмплов в ld.so при тех же условиях; вероятно, артефакт SIGPROF-preload.
Эти сэмплы не стоит интерпретировать как стоимость эмулятора.

## 3. Ревью PR #9 и PR #10 относительно baseline

Baseline для обоих — `main` `27b1b7c` с `OPT_JIT_BLOCK_TRACE=OFF` (код ядра
идентичен базам PR #9 `c50d2fa` и PR #10 `91774d5` при выключенном trace).
PR #9 и #10 — **не** последовательные версии: #9 (стек на #8) меняет тело
C++ helper; #10 (стек на #7) не меняет `src/`, а хранит отдельный патч
`experimental-inline.patch.b64`, который убирает вызов helper из JIT.

### PR #9 — `FPU_FLD_32` использует `mem_readd_inline`

- **Семантика:** идентична baseline по построению (`mem_readd<op>` — это
  `mem_readd_inline<op>`), включая breakpoints, unaligned и handler пути и
  legacy page fault. Подтверждено `PFPREC` (вывод base и pr9 совпадает на
  обоих ядрах). Отклонение S4 baseline наследуется.
- **Машинный код:** 20 → 120 B; быстрый путь теряет вызов `mem_readd` и
  его 4 push/pop. Остальной путь (вызов из JIT, сохранение volatile-регистров,
  `PUSHFQ`) не меняется.
- **Компромиссы:** минимальный риск, минимальный потенциал (меньше 7.3%,
  реально — доля пролога/эпилога и call/ret). Альтернатива с более широким
  эффектом: сделать сам `mem_readd` «тонким» (вынести unaligned/handler путь
  в `[[gnu::noinline, gnu::cold]]`), тогда выигрыш получат и `FPU_FLD_64`,
  normal core и прочие C++-вызовы.
- **Тесты PR #9:** дифференциальные (base ↔ candidate) и потому способны
  обнаружить только расхождение двух реализаций, а не общее отклонение от
  архитектуры. Для однострочного семантически нейтрального изменения этого
  достаточно; для утверждений о «корректной обработке #PF» — нет.

### PR #10 — проверенное inline-чтение в JIT для x87 m32

Изменение: в `dh_fpu_esc0/1/2/3` вызов `FPU_FLD_32` заменён на
`dyn_read_word_release(EA, TMPW, true)` + `gen_save_host(&temp.m1)`.

| Область | Оценка | Детали |
|---|---|---|
| x87 стек, CW/SW | Без изменений | Чтение выполняется до host x87 операции; при fault x87 ещё не тронут, рестарт безопасен. Хранилище `temp.m1` то же. |
| Masked/unmasked x87 исключения | Без изменений | Host CW всегда маскирован (`|0x3f`), `FWAIT` no-op → #MF не доставляется ни в baseline, ни в PR #10 (pre-existing, S12) |
| Page faults | **Изменение поведения** | baseline: вложенный `PAGING_PageFault`, guest видит EIP начала блока и устаревшие регистры, helper продолжает чтение после возврата обработчика (а не рестарт). PR #10: точное исключение `DynRunException`, EIP = инструкция, регистры сохранены, инструкция перезапускается. Проверено `PFPREC` (S4/S5) |
| Пересечение страниц | Эквивалентно по данным | Оба используют побайтный путь при смещении ≥ 0xFFD; PR #10 — `_checked` вариант. `PFPREC fld32x`: E=I, V=ok |
| CPL3, R/W, segment limits | Без изменений относительно integer-загрузок | Механизм `InitPageCheckOnly` тот же, что у всех integer-загрузок dynamic core; limits не проверяются ни там, ни там (общая особенность ядра) |
| MMIO / VGA | Эквивалентно | `readd_checked` → `readd`; один вызов handler на выровненное чтение; cross-page — 4 побайтных |
| Debugger | **Регрессия только в heavy debugger** (по исходнику, не исполнялось) | Быстрый путь без `DEBUG_UpdateMemoryReadBreakpoints` → BPMR на x87 m32 не сработает при попадании в TLB (как уже для integer-загрузок dynamic core) |
| SMC / инвалидация | Без изменений | Чтение кода не перехватывается ни там, ни там; тест SMC из PR #10 — дифференциальный |
| Флаги, порядок исключений, повтор | Корректно | `gen_protectflags` перед проверкой; `eip_change = op_start` → рестарт с начала x87-инструкции; повторный вход не делает повторный `FRSTOR` (state_used=1) |
| Размер кода / I-cache | +2.6–2.9× для x87-блоков, +5.8% всего JIT | Деферред-заглушки исключений и встроенный slow path; `CacheBlock overrun` маловероятен (S11, запас ~2.7×). По perf, self-время x87-блоков не выросло (0x306bd ~100 сэмплов до и после) — одиночные прогоны |
| Сопровождаемость | Слабое место | Смешанная семантика внутри одного ядра: m32 загрузки точные, m16/m64/m80 и все stores — legacy; патч хранится как base64 вне ветки кода; предупреждение `-Wunused-function` |

**Риски по приоритету (PR #10):**

1. *Изменение семантики #PF для x87 m32* — функция `dh_fpu_read32_experiment`,
   инструкции `D8 /r`, `D9 /0`, `DA /r`, `DB /0` с memory-операндом;
   воспроизведение — `tests/pfprec.asm`; ожидаемая семантика — SDM vol.3
   §6.15: сохранённый CS:EIP указывает на faulting-инструкцию. PR #10 ближе к
   архитектуре, но любой продукт-PR должен заявлять это как behaviour change и
   покрывать остальные x87-формы, иначе ядро ведёт себя непоследовательно.
2. *Heavy-debugger BPMR* — `dyn_read_word` fast path; воспроизведение —
   сборка `OPT_HEAVY_DEBUGGER=ON` + test hook, ставящий BPMR на адрес
   операнда до исполнения (hooks PR #9 срабатывают внутри `FPU_FLD_32`,
   который в PR #10 не вызывается, поэтому их нужно переписать); ожидание —
   флаг breakpoint при чтении операнда x87-инструкцией.
3. *Рост кода* — `dyn_read_word` + `dyn_check_bool_exception_al` на каждую
   x87 m32-загрузку; ожидаемо безопасно при текущем лимите (S11).

### Отдельно: ограничение #MF/FWAIT

Не связано с PR #9/#10: host x87 всегда работает с замаскированными
исключениями, `WAIT/FWAIT` — no-op в обоих ядрах; normal core тоже не
доставляет #MF (наблюдение PR #9). Любая работа над x87 lowering должна
явно сохранять это поведение или исправлять его отдельным изменением с
собственными тестами.

## 5. Рекомендация

1. **Не продолжать PR #9** (исчерпан) и **не продвигать PR #10 «как есть»**
   (смешивает ускорение с изменением семантики, не покрывает остальные
   x87-формы, ломает heavy-debugger BPMR на быстром пути).
2. **Следующая оптимизация — C1a:** inline TLB fast path для x87 m32 с
   промахом в legacy-путь (`mem_readd`), т.е. выигрыш PR #10 (≈+9% на этом
   хосте, evidence P3) без изменения семантики. Наибольшая доказанно устранимая стоимость среди
   низкорисковых кандидатов (152 M вызовов, ≈7.3% окна + JIT-сторона), fast
   path уже показан на 99.98% загрузок, эквивалентность проверяется побайтным
   совпадением `tests/pfprec.asm` с baseline, эффект — счётчиками.
3. **Сразу за ней — C2** (PUSH/POP через существующие `dyn_read_word`/
   `dyn_write_word`): тот же механизм, ещё меньше кода, семантика неизменна.
4. **Отдельная исследовательская линия — C4 (флаги, ≈9%)**: сначала
   стоимость `POPFQ` на целевых AMD-хостах и дифференциальный тест флагов
   против normal core, затем точное дешёвое восстановление флагов без
   `POPFQ`.
5. **Самый дешёвый безопасный шаг — C6** (`BT`/`SETcc`/`SAHF`/`LAHF` в
   dynamic core, ≈1.5%): можно первым отдельным PR, гейт `tests/bitops.asm`.
6. **Корректность отдельно:** точные #PF для всех x87 memory-форм в dynamic
   core — самостоятельное исправление с `pfprec` (все случаи → `E=I R=ok`).
7. **Измерения времени** — только на выделенном хосте с A/A-плацебо; на
   облачном хосте использовать точные счётчики и инъекции стоимости.
