# Phase 2 — план экспериментов

Цель Phase 2 — опровергнуть или подтвердить два лучших кандидата
([candidates.md](candidates.md)): **C1a** (inline fast path для x87 m32 с
промахом в legacy-путь `mem_readd`) и **C2** (inline fast path для PUSH/POP).
Параллельно — подготовительные эксперименты для C4 (флаги), C3 и C6.
Каждый эксперимент имеет заранее объявленный критерий опровержения. Корректность проверяется отдельно от скорости.

## M0. Инфраструктура измерения (обязательна перед C1a/C2)

**Почему:** на общем облачном хосте даже детерминированная гостевая
нагрузка даёт CV 7–10% CPU-времени (evidence P1). Значит, «работа» и
«время» мерятся разными инструментами.

1. **Детерминированные частоты.** Сборка `JitCounters`
   (`instrumentation/apply_jit_counters.py`) + `tools/count_quake.py`
   (fixed cycles 1 000 000, lag mode, снимки SIGUSR1 в начале и конце demo).
   - Критерий пригодности (выполнен в Phase 1): guest-результаты совпадают
     с base; два прогона совпадают в пределах 0.3%.
   - Для каждого кандидата добавить счётчик устраняемого события до
     реализации и проверить его падение после.
   - callgrind на DOSBox JIT в облачном окружении непригоден (evidence P5);
     на выделенном хосте можно повторить с `--smc-check=all-non-file` и
     коротким окном (несколько кадров) для Ir.
2. **Стоимость на событие in situ.** Инъекция K дополнительных
   семантически нейтральных экземпляров операции
   (`instrumentation/apply_flag_injection.py` как образец): наклон
   «время / число инъекций» устойчив к шуму, т.к. эффект в разы больше
   A/A-плацебо.
3. **Время.** Только на выделенном хосте (bare metal или VM без
   overcommit, фиксированная частота, turbo off, `isolcpus`/`taskset` для
   main thread). Кандидат — окружение engineering-lab#2 (заявлен CV 2.17%,
   MDE ≈1% CPU-времени): сначала опубликовать его A/A-данные и повторить
   PR #10 против base с двумя плацебо-метками (ожидание ≈+9%). Протокол — `tools/bench_quake.py` с fixed cycles (метрика
   `demo_cpu_s`) и, для сравнения с прошлым, `--cycles max` (FPS).
   - Сначала A/A: ≥16 блоков; принять хост, если |плацебо| < 1% и ширина
     bootstrap-интервала < 2%. Иначе — не делать выводов о малых эффектах.
4. **Hardware counters**, если доступен PMU: `perf stat -e
   cycles,instructions,branch-misses,L1-icache-load-misses` на окно demo.

## E1. C1a — x87 m32 fast path с промахом в legacy-путь

**Изменение:** в `dh_fpu_esc0/1/2/3` (только memory m32 load формы) —
inline TLB проверка как в `dyn_read_word` (в пределах страницы и
`tlb.read != null` → `mov` в `temp.m1`); при промахе/пересечении страницы —
legacy-чтение (`*dst = mem_readd(addr)`, `mem_unalignedreadd`) без
`_checked` helpers и без deferred exception stubs. Минимальная форма —
`dyn_read_word` с параметризованными slow-path функциями.

**Почему не PR #10:** сохраняет legacy-семантику #PF полностью (тот же
helper на промахе), поэтому `tests/pfprec.asm` должен давать **побайтно тот
же вывод, что baseline** (E=B R=stale для x87) — это и есть тест
эквивалентности. Отдельно, позже, — correctness-изменение «точные #PF для
всех x87 memory-форм», где `pfprec` должен стать `E=I R=ok` везде.

**Корректность:** `pfprec` (эквивалентность baseline), `jitsize` (размер
блока < лимита с запасом), оракулы PR #10 (`FPU_FLAGS`, `FPU_PF*`,
`FPU_USER*`), heavy-debugger BPMR (ожидаемо: при TLB-попадании BPMR
пропускается, как у integer-загрузок — задокументировать или вызывать hook
в debugger-сборке).

**Опровержение (детерминированное):**
- `pfprec` на C1a ≠ base побайтно → семантика изменилась → отклонить
  реализацию;
- вызовы legacy slow path в окне demo должны быть ≈ числу TLB-промахов PR #10
  (≈31 k вместо 152 M); иначе fast path не срабатывает;
- на выделенном хосте: ускорение < 3.5% (половина helper-доли) при
  идентичной гостевой работе → модель стоимости неверна.

**Сравнение с PR #9 и PR #10:** тот же протокол счётчиков для всех трёх
(база данных уже есть в evidence §4); это сразу показывает, какая доля
выигрыша PR #10 происходит от устранения helper, а какая — от изменения
семантики/кода.

## E2. C2 — inline fast path для стековых PUSH/POP

**Изменение (минимальное):** в `dyn_push` заменить
`gen_call_function(mem_writed_checked/mem_writew_checked)` +
`dyn_check_bool_exception_al()` на `dyn_write_word(DREG(STACK), dynreg,
decode.big_op)` с последующей записью `NEWESP → ESP` (порядок сохраняется:
ESP меняется только после успешной записи). В `dyn_pop(checked=true)` —
`dyn_read_word(DREG(STACK), dynreg/TMPW, decode.big_op)`. `dyn_push_unchecked`
и `dyn_pop(..., false)` (PUSHA/POPA/LEAVE) не трогать в первой итерации.

**Корректность (до любых замеров времени):**
- DOS-тесты (новые, рядом с `tests/pfprec.asm`): push/pop dword и word на
  границе страницы (смещения 0xFFC–0xFFF); #PF при push в
  отсутствующую страницу стека — ESP не изменился, сохранённый EIP = PUSH,
  повтор успешен; то же для POP; CPL3 стек в supervisor-странице (#PF
  err=7/5); 16-битный стек (`cpu.stack.mask = 0xFFFF`) с переполнением SP
  через 0; `PUSH ESP`/`POP ESP`; `CALL`/`RET` через границу страницы.
- Ожидаемая семантика: SDM vol.2 PUSH/POP (декремент после успешной
  записи, `POP ESP` загружает значение до инкремента), vol.3 §6.15.
- Все тесты — на normal и dynamic, base и кандидат; сравнивать с
  ожидаемыми значениями, а не только между собой.
- Quake demo1: 969 кадров, guest seconds/fps в lag mode идентичны base.

**Опровержение (детерминированное):**
- `push_helper_calls` + `pop_helper_calls` (105 M в base) должны упасть
  > 90%; если нет — стек не попадает в прямой TLB → механизм неверен;
- на выделенном хосте: отсутствие ускорения при падении счётчиков →
  inline-код не дешевле вызова → C2 отвергнут.

**Измерение времени:** M0.3 на выделенном хосте, ≥16 рандомизированных
блоков base/кандидат + A/A-плацебо в том же расписании.

## E3 (параллельно). C4 — флаги

Частоты уже измерены (604 M `PUSHFQ`, 37.3 M `POPFQ`), стоимость in situ на
Intel — ≈10–12 нс / ≈0.3 нс. Дальше:
1. Повторить `microbench/flags_save.c` и инъекцию
   (`apply_flag_injection.py popf 4`) на целевых AMD Zen 3/4. Опровержение:
   `POPFQ` < 2 нс in situ → вклад < 1.5% → снизить приоритет.
2. Распределение `POPFQ` по блокам (счётчик на сайт) — какие guest-паттерны
   (`ADC`-цепочки через загрузку?) их порождают.
3. Дифференциальный тест флагов против normal core (все ALU-операции ×
   входные флаги × memory-операнд между производителем и потребителем) —
   до любой реализации (a)/(b)/(c).

## E4 (дешёвый). C3 — входы в dispatcher

18.0 M входов/окно ≈11 нс каждый (≈3.6%). Зонд Phase 1: 67.5% входов —
в ту же code page, что предыдущий (критерий «> 50%» пройден). Дальше —
прототип «skip MakeCodePage для той же валидной code page» и тесты SMC,
смены CR3/INVLPG и CS/режима между RET; опровержение — счётчик `MakeCodePage`
не падает примерно на 2/3 или любой тест расходится с normal core.

## E5 (дешёвый, низкий риск). C6 — `BT`/`SETcc`/`SAHF`/`LAHF` в dynamic core

1.95 M fallback в normal core за окно, все `BR_Opcode` (см. candidates C6).
- **Изменение:** регистровые формы `BT/BTS/BTR/BTC`, `SETcc r/m8`,
  `SAHF`/`LAHF`; memory-формы `BTx` оставить на fallback.
- **Корректность:** `tests/bitops.asm` (34 случая, CF через `SBB`, memory
  bit string, 16-бит, x87-идиомы сравнения) — 0 отклонений на normal и
  dynamic; тест kaaburgh/dosbox-staging#11 как дополнительный; Quake demo1 —
  идентичные guest-результаты в lag mode.
- **Опровержение:** `fallback_opcode` не падает до ≈60 k (системные
  инструкции CWSDPMI) → реализация не покрывает горячие формы; блоки в дампе
  всё ещё заканчиваются на `0F A3`/`9E`/`0F 94` → то же.
- **Время:** ожидаемый эффект мал (≈1–2%) — только на тихом хосте
  (см. M0.3 и пол измерений из engineering-lab#2, если он подтвердится).

## Общие правила

- Сначала корректность (тесты с ожидаемыми архитектурными значениями,
  normal core как дополнительный оракул), потом точные счётчики, потом время.
- Каждое изменение — отдельный draft PR в `kaaburgh/dosbox-staging`
  от `main`, без смешивания с инструментированием.
- Отчёт по каждому эксперименту: SHA исходников и бинарников, команды,
  guest-результаты, счётчики событий, A/A-плацебо, интервалы; отрицательные
  результаты публикуются так же, как положительные.
